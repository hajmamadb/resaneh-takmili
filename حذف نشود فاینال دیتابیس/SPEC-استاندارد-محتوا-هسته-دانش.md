## ۱. هدف و دامنه سند

این سند استاندارد ثبت، نگهداری، اعتبارسنجی و انتشار محتوای علمی در هسته دانش ارتباطات و رسانه را تعریف می‌کند. هدف، ایجاد مجموعه‌ای از مدخل‌های علمی مستقل، مستند، قابل جست‌وجو و مرتبط با یکدیگر است؛ به‌گونه‌ای که داده‌ها علاوه بر نمایش انسانی، برای جست‌وجوی معنایی، تحلیل روابط، بازیابی دانش و پردازش ماشینی نیز مناسب باشند.

این سند باید به‌عنوان مرجع محتوایی بخش `Knowledge` در نرم‌افزارهای کدنویسی و ابزارهای هوش مصنوعی مورد استفاده قرار گیرد. عامل کدنویس باید هنگام طراحی یا تغییر فرم‌ها، مدل داده، API، اعتبارسنجی، پنل مدیریت و رابط کاربری، الزامات این سند را رعایت کند.

### ۱.۱. اصول بنیادین

1. هر نوع موجودیت باید ساختار محتوایی متناسب با ماهیت علمی خود داشته باشد.
2. اطلاعات مشترک میان موجودیت‌ها باید در لایه مشترک نگهداری شود و تکرار غیرضروری نداشته باشد.
3. محتوای علمی، فکت‌ها، روابط و منابع باید از یکدیگر تفکیک شوند.
4. هر ادعای علمی مهم باید تا حد امکان به منبع و محل دقیق استناد متصل باشد.
5. نبود اطلاعات با «نامرتبط بودن»، «نامشخص بودن» و «ثبت‌نشدن» یکسان نیست.
6. فیلدهای شرطی نباید با داده ساختگی یا مقدار پیش‌فرض غیرواقعی تکمیل شوند.
7. روابط میان موجودیت‌ها باید نوع‌دار، جهت‌دار، قابل استناد و قابل اعتبارسنجی باشند.
8. متن آزاد جایگزین داده ساختاریافته نیست؛ هرجا امکان استخراج داده به فیلد مستقل وجود دارد، باید از فیلد مستقل استفاده شود.
9. استاندارد حجم محتوا معیار کنترل کیفیت است، نه مجوز تولید متن تکراری یا کم‌ارزش.
10. وضعیت تکمیل محتوا، وضعیت بررسی علمی و وضعیت انتشار باید مستقل از یکدیگر باشند.

### ۲.۴. لایه چهارم: فکت‌ها و گزاره‌های علمی

فکت یا گزاره علمی باید به‌صورت واحدی مستقل، قابل جست‌وجو و قابل استناد ثبت شود.

ساختار پیشنهادی:

| فیلد | نام فنی | توضیح |
|---|---|---|
| شناسه فکت | `fact_id` | شناسه یکتا |

| منبع/شواهد | `evidence_ids` | شواهد پشتیبان |

قواعد:
- فکت باید تا حد امکان اتمی باشد؛ هر فکت یک ادعای مستقل را بیان کند.
- چند ادعا در یک فکت مرکب ذخیره نشود.
- فکت‌های مورد اختلاف باید با دیدگاه‌ها و منابع متفاوت ثبت شوند؛ اختلاف نباید با حذف یکی از دیدگاه‌ها پنهان شود.
- «فکت تأییدشده» باید شواهد قابل ردیابی داشته باشد.
- فکت استنباطی باید از فکت مستقیم منبع متمایز شود.

4. منابع ثانویه معتبر برای تفسیر، نقد و مرور ادبیات استفاده شوند.
5. منبع وبی باید URL و تاریخ دسترسی داشته باشد.
6. DOI و URL نباید حدس زده یا ساخته شوند.

## ۳. استاندارد حجم و سطح تکمیل محتوا

### ۳.۱. قواعد شمارش کلمات

1. شمارش کلمات بر اساس متن محتوایی فارسی یا زبان اصلی مدخل انجام می‌شود.
2. عنوان‌ها، شناسه‌ها، فهرست منابع، فراداده، برچسب‌ها و نام فیلدها در شمارش متن اصلی لحاظ نمی‌شوند.
3. جدول‌ها و فهرست‌های داده‌ای به‌تنهایی جایگزین تحلیل متنی نیستند.
4. تکرار یک تعریف در چند بخش برای رسیدن به حداقل کلمات مجاز نیست.
5. حداقل حجم، شرط لازم است نه شرط کافی.
6. بخش‌هایی که ماهیت عددی، نموداری یا ساختاریافته دارند با تعداد کلمه سنجیده نمی‌شوند؛ معیار آن‌ها تعداد اجزا، روابط یا داده‌های لازم است.

### ۳.۲. سطح‌های محتوایی

| سطح | تعریف | معیار کلی |
|---|---|---|
| پایه | مدخل اولیه قابل شناسایی | هویت، تعریف، دسته‌بندی، بخش‌های ضروری و منبع اولیه |
| استاندارد | مدخل قابل استفاده پژوهشی | تکمیل بخش‌های الزامی، روابط، فکت‌ها و استنادهای اصلی |
| جامع | مدخل مرجع تخصصی | تحلیل تاریخی/تطبیقی، نقدها، شواهد گسترده و روابط غنی |

سطح پایه نباید به‌عنوان مدخل علمی کامل معرفی شود. سطح استاندارد هدف انتشار عادی است. سطح جامع برای مدخل‌های کلیدی و پرتکرار اولویت دارد.

#### قواعد اعتبارسنجی

- نقدها باید به منتقد یا منبع مشخص متصل شوند.

### ۴.۳. مفهوم (Concept)

## ۵. قواعد فیلدهای اجباری، شرطی و اختیاری

هر فیلد باید یکی از سه وضعیت زیر را داشته باشد:

| وضعیت | تعریف | رفتار سامانه |
|---|---|---|
| اجباری (`required`) | برای ثبت معتبر رکورد لازم است | بدون مقدار معتبر، ثبت/انتشار متوقف شود |
| شرطی (`conditional`) | در صورت تحقق شرط مشخص لازم است | بر اساس شرط فعال شود |
| اختیاری (`optional`) | برای غنی‌سازی رکورد است | نبود آن مانع ثبت یا انتشار نیست |

### ۵.۱. وضعیت نبود داده

برای فیلدهای مهم، مقدار خالی نباید چند معنا داشته باشد. وضعیت داده باید یکی از این موارد باشد:

- `known`: مقدار معلوم و ثبت‌شده است.
- `unknown`: بررسی شده، اما مقدار نامعلوم است.
- `not_applicable`: این فیلد برای این رکورد موضوعیت ندارد.
- `not_researched`: هنوز بررسی نشده است.
- `disputed`: منابع یا دیدگاه‌ها اختلاف دارند.
- `withheld`: به دلیل سیاست یا محدودیت، نمایش داده نمی‌شود.

این وضعیت‌ها باید از مقدار واقعی فیلد مستقل باشند.

### ۵.۲. قواعد محتوای شرطی

نمونه:
- تاریخ وفات برای شخص زنده `not_applicable` است.
- فرمول برای شاخصی که محاسبه عددی ندارد `not_applicable` است.
- نمودار برای مدلی که نمایش بصری معنادار ندارد می‌تواند اختیاری باشد.
- ابزار سنجش برای سازه‌ای که هنوز ابزار استاندارد ندارد نباید ساختگی ثبت شود.

### ۷.۲. اصل طراحی ترکیبی

- فیلدهای هویتی و عملیاتی پرتکرار، ساختاریافته و قابل ایندکس باشند.
- بخش‌های محتوایی هر موجودیت بر اساس Schema نسخه‌پذیر تعریف شوند.
- داده‌های پرتکرار و قابل فیلتر مانند سال، نوع، وضعیت، نقش و سطح تحلیل در فیلدهای مستقل ذخیره شوند.
- متن تحلیلی در فیلدهای متن غنی یا ساختار محتوایی مناسب نگهداری شود.
- روابط، فکت‌ها و منابع در ساختارهای مستقل ذخیره شوند.
- استفاده از JSON برای بخش‌های منعطف مجاز است، اما نباید جایگزین جداول رابطه‌ای مورد نیاز برای جست‌وجو، گزارش‌گیری، یکپارچگی و روابط شود.

### ۷.۳. نسخه‌بندی Schema

هر نوع موجودیت باید نسخه Schema داشته باشد:

- `schema_key`

- `display_order`

تغییر Schema نباید داده‌های قبلی را بدون مهاجرت کنترل‌شده خراب کند.

### ۷.۴. API و رابط کاربری

- فرم هر موجودیت باید از Schema همان نوع تولید یا پیکربندی شود.
- بخش‌های مشترک در کامپوننت‌های مشترک نمایش داده شوند.
- بخش‌های اختصاصی نباید با فرم عمومی و یکسان جایگزین شوند.
- امکان ذخیره پیش‌نویس و تکمیل تدریجی وجود داشته باشد.
- وضعیت هر بخش و میزان تکمیل رکورد نمایش داده شود.
- فیلدهای شرطی بر اساس قواعد Schema فعال یا غیرفعال شوند.
- منابع و روابط باید از طریق انتخاب موجودیت‌های موجود ثبت شوند؛ ایجاد رکورد تکراری به‌جای اتصال به رکورد موجود مجاز نباشد.

## ۹. دستورالعمل اجرایی برای عامل کدنویس

این بخش برای استفاده مستقیم در ابزارهای کدنویسی هوش مصنوعی نوشته شده است.

### مأموریت

استاندارد محتوایی و ساختاری هسته دانش را بر اساس این سند پیاده‌سازی یا با معماری موجود پروژه تطبیق بده.

### قواعد غیرقابل مذاکره

1. ابتدا معماری فعلی پروژه، مدل داده، فرم‌ها، APIها، مجوزها و گردش‌کار موجود را بررسی کن.
2. پیش از بررسی، هیچ فایل، جدول، فیلد یا قابلیت موجود را حذف یا بازنویسی نکن.
3. این سند را مرجع محتوایی بدان، اما آن را مجوز تغییر خودسرانه معماری فنی پروژه تلقی نکن.
4. هر یک از ۱۵ نوع موجودیت باید Schema اختصاصی داشته باشد.
5. لایه‌های مشترک هویت، طبقه‌بندی، فکت، روابط، منابع و کنترل کیفیت باید تا حد امکان مشترک و قابل استفاده مجدد باشند.
6. ساختار محتوایی هر نوع موجودیت باید قابل نسخه‌بندی باشد.
7. فیلدهای اجباری، شرطی و اختیاری باید در Schema مشخص شوند.
8. وضعیت‌های `unknown`، `not_applicable`، `not_researched` و `disputed` باید از مقدار خالی متمایز باشند.
9. فکت‌ها، روابط و منابع باید مستقل و قابل استناد باشند.
10. منبع یا رابطه ساختگی تولید نکن.
11. برای داده‌های موجود، مهاجرت مخرب یا حذف اطلاعات انجام نده.
12. تغییرات باید با تست واحد، تست یکپارچگی و تست رابط کاربری بررسی شوند.
13. اگر بخشی از سند با معماری موجود تعارض دارد، ابتدا تعارض و گزینه‌های حل آن را مستند کن؛ بدون تأیید، تغییر مخرب انجام نده.
14. هیچ‌یک از معیارهای حجم محتوا نباید باعث تولید متن تکراری یا محتوای بی‌منبع شود.
15. تأیید علمی انسانی را با امتیاز خودکار جایگزین نکن.

### خروجی‌های مورد انتظار

1. گزارش وضعیت فعلی و فاصله آن با این استاندارد.
2. ماتریس تطبیق ۱۵ موجودیت با ساختار فعلی.
3. طراحی Schema نهایی و نسخه‌بندی آن.
4. طراحی مدل داده و روابط.
5. طراحی فرم‌ها و قواعد اعتبارسنجی.
6. طراحی گردش‌کار منابع، فکت‌ها و بازبینی علمی.
7. برنامه مهاجرت سازگار با داده‌های موجود.
8. تست‌های پذیرش برای هر نوع موجودیت.
9. مستندات فنی و راهنمای مدیر محتوا.

### ترتیب اجرای پیشنهادی

- مرحله ۱: ممیزی فقط‌خواندنی وضعیت فعلی.
- مرحله ۲: تهیه ماتریس شکاف و شناسایی تعارض‌ها.
- مرحله ۳: طراحی مدل مفهومی و Schema.
- مرحله ۴: تأیید طراحی پیش از تغییرات.
- مرحله ۵: پیاده‌سازی لایه مشترک.
- مرحله ۶: پیاده‌سازی ۱۵ Schema اختصاصی.
- مرحله ۷: پیاده‌سازی فکت، رابطه و منبع.
- مرحله ۸: پیاده‌سازی اعتبارسنجی و کنترل کیفیت.
- مرحله ۹: مهاجرت امن داده‌های موجود.
- مرحله ۱۰: تست، مستندسازی و تحویل.

## ۱۰. تصمیم‌های باز و موارد نیازمند تأیید محصول

موارد زیر باید در سطح محصول نهایی شوند و عامل کدنویس نباید بدون بررسی پروژه درباره آن‌ها فرض قطعی بسازد:

1. انتخاب معماری ذخیره محتوا: ثابت، پویا یا ترکیبی. پیشنهاد این سند: ترکیبی.
2. اتصال منابع: سطح رکورد، بخش و فکت. پیشنهاد این سند: پشتیبانی از هر سه سطح.
3. اعتبارسنجی علمی: خودکار، انسانی یا ترکیبی. پیشنهاد این سند: کنترل خودکار به‌علاوه تأیید متخصص.
4. سیاست انتشار مدخل‌های پایه: انتشار عمومی، نمایش با برچسب ناقص یا صرفاً استفاده داخلی.
5. نقش‌ها و مجوزهای ایجاد، ویرایش، ارزیابی و انتشار.
6. سیاست منابع قابل قبول و اولویت منابع اولیه.
7. سیاست نمایش اختلاف‌های علمی و دیدگاه‌های رقیب.
8. سیاست نسخه‌بندی و نگهداری تاریخچه تغییرات.

## ۱۲. اصل نهایی

هسته دانش باید هم‌زمان سه ویژگی داشته باشد:

1. **دانشنامه‌ای:** محتوای روشن، ساختاریافته و قابل فهم برای انسان.
2. **مستند:** فکت‌ها و ادعاهای علمی قابل ردیابی تا منبع و محل استناد.
3. **رابطه‌مند و ماشین‌خوان:** موجودیت‌ها، ویژگی‌ها و روابط دارای ساختار استاندارد برای جست‌وجو، تحلیل و پردازش ماشینی.

هیچ‌یک از این سه ویژگی نباید فدای دو ویژگی دیگر شود. کیفیت نهایی سامانه با تعداد رکوردها یا حجم متن سنجیده نمی‌شود؛ معیار اصلی، دقت علمی، قابلیت ردیابی، تمایز مفهومی، کامل‌بودن متناسب با نوع موجودیت و صحت روابط دانش است.
